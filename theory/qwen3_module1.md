### 📚 Ключевые темы (с пояснениями)

#### 1. `http.ListenAndServe`, `http.Server`, таймауты
- **`http.ListenAndServe(addr, handler)`** — самая простая команда для запуска сервера.  
  👉 *Простыми словами:* «Слушай такой-то адрес и обрабатывай запросы вот этим обработчиком».
- **`http.Server`** — более гибкий способ настройки сервера. Позволяет задать:
  - `ReadTimeout` — сколько ждать, пока клиент пришлёт запрос (защита от «медленных» клиентов)
  - `WriteTimeout` — сколько ждать, пока сервер отправит ответ
  - `IdleTimeout` — сколько держать открытым соединение без активности
  > 💡 **Важно:** без таймаутов злоумышленник может «подвесить» сервер, отправив много медленных запросов.

## 📌 1. `http.ListenAndServe` — «Кнопка запуска»
- **Что это:** Самая короткая команда для старта HTTP-сервера в Go.
  ```go
  http.ListenAndServe(":8080", nil)
  ```
- **Как работает под капотом:**
    1. Создаёт объект `http.Server` со стандартными настройками.
    2. Начинает слушать порт `:8080`.
    3. Блокирует выполнение программы навсегда (или пока не упадёт).
- **Плюсы:** Идеально для быстрых прототипов и обучения.
- **Минусы:**
    - 🔒 Не даёт настроить таймауты → сервер уязвим к зависаниям.
    - 🚫 Не позволяет плавно завершить работу.
    - ⚠️ Возвращает ошибку только при критическом сбое старта (например, порт уже занят). Ошибки обработки запросов теряются.
- **Вывод:** Используйте только в учебных скриптах. В реальных проектах — сразу переходите к `http.Server`.

---

## 🎛 2. `http.Server` — «Пульт управления»
- **Что это:** Структура, которая описывает все параметры вашего сервера. Вы настраиваете её вручную, а потом запускаете.
  ```go
  srv := &http.Server{
      Addr:         ":8080",
      Handler:      myRouter,
      ReadTimeout:  5 * time.Second,
      WriteTimeout: 10 * time.Second,
      IdleTimeout:  60 * time.Second,
  }
  srv.ListenAndServe()
  ```
- **Почему это лучше:**
    - ✅ Полный контроль над жизненным циклом запросов.
    - ✅ Легко добавить graceful shutdown, метрики, кастомные обработчики ошибок.
    - ✅ Безопасно по умолчанию, если правильно выставить таймауты.
- **Важный нюанс:** `Handler` — это ваш маршрутизатор (роутер). Если передать `nil`, Go автоматически подставит стандартный `http.DefaultServeMux`.

## ⏱ 3. Таймауты: зачем они и как работают
Таймауты — это «ограничители времени», которые не дают одному клиенту бесконечно занимать соединение. Без них сервер быстро исчерпает лимит подключений и перестанет отвечать.

| Таймаут | Что ограничивает | Простая аналогия | Рекомендуемое значение (для REST API) |
|---------|------------------|------------------|---------------------------------------|
| `ReadHeaderTimeout` | Время на чтение **только заголовков** запроса | «Сколько ждать, пока клиент скажет, что ему нужно» | `5–10 сек` |
| `ReadTimeout` | Время на чтение **всего запроса** (заголовки + тело) | «Сколько ждать, пока клиент полностью передаст файл/JSON» | `10–15 сек` |
| `WriteTimeout` | Время на отправку **всего ответа** клиенту | «Сколько ждать, пока клиент заберёт ваш ответ» | `15–30 сек` |
| `IdleTimeout` | Время ожидания **следующего запроса** на том же соединении (Keep-Alive) | «Сколько держать столик пустым, если клиент отошёл» | `60–120 сек` |

### 🔍 Разберём на примере:
- Клиент подключается → сервер ждёт заголовки (`ReadHeaderTimeout`).
- Заголовки пришли → сервер ждёт тело запроса, если оно есть (`ReadTimeout`).
- Запрос обработан → сервер формирует ответ и отправляет (`WriteTimeout`).
- Ответ ушёл → соединение остаётся открытым для следующего запроса (`IdleTimeout`). Если клиент молчит дольше → соединение закрывается, ресурсы освобождаются.

---

## 🛡 4. Защита от атак: почему таймауты — это безопасность
Без таймаутов ваш сервер уязвим к атаке **Slowloris**:
- Злоумышленник открывает сотни соединений и отправляет по 1 байту в секунду.
- Сервер думает, что «клиент ещё грузит запрос», и держит соединения открытыми.
- Через 5 минут все слоты заняты, реальные клиенты получают `503 Service Unavailable`.

**Как защититься:**
1. Всегда ставьте `ReadHeaderTimeout` (защищает от Slowloris).
2. `ReadTimeout` должен быть меньше, чем таймаут балансировщика или reverse-proxy (Nginx, Cloudflare).
3. `WriteTimeout` спасает от клиентов, которые медленно скачивают большие файлы, забивая память сервера.
4. `IdleTimeout` экономит оперативную память, вовремя закрывая «мёртвые» соединения.

---

## 💡 5. Важные моменты для запоминания
- ✅ **Никогда не используйте `http.ListenAndServe` в production.** Всегда создавайте `&http.Server{}` вручную.
- ✅ `ReadHeaderTimeout` важнее `ReadTimeout` для большинства API. Если не знаете, что выбрать → ставьте оба, но `ReadHeaderTimeout` должен быть короче.
- ✅ Таймауты считаются **на одно соединение**, а не на весь сервер. Если у вас 1000 одновременных запросов, каждый из них будет ждать своё время.
- ✅ Таймауты `WriteTimeout` и `IdleTimeout` начинают отсчёт **после** отправки заголовков ответа. Если ваш обработчик думает 10 секунд, `WriteTimeout` ещё не запущен.
- ⚠️ Если обработчик работает дольше таймаута, Go **не прервёт его автоматически**. Он просто закроет соединение, а горутина обработчика продолжит работать в фоне (утечка ресурсов). Для принудительной отмены используйте `context.WithTimeout` внутри хендлера.

#### 2. Интерфейсы `http.Handler` и `http.HandlerFunc`
- **`http.Handler`** — интерфейс с одним методом: `ServeHTTP(w, r)`.  
  👉 *Простыми словами:* «Любой объект, который умеет отвечать на запрос, — это обработчик».
- **`http.HandlerFunc`** — функция-обёртка, которая позволяет использовать обычную функцию как обработчик.
  ```go
  // Пример: функция становится обработчиком
  func myHandler(w http.ResponseWriter, r *http.Request) {
      fmt.Fprintln(w, "Привет!")
  }
  http.HandleFunc("/", myHandler) // автоматически превращает функцию в HandlerFunc
  ```

> *Простыми словами: как в Go заставить любую функцию или структуру отвечать на HTTP-запросы, не изобретая велосипед*

## 📌 1. `http.Handler` — «Единый контракт для всех обработчиков»
- **Что это:** В стандартной библиотеке Go существует всего **один интерфейс** для обработки HTTP-запросов:
  ```go
  type Handler interface {
      ServeHTTP(w http.ResponseWriter, r *http.Request)
  }
  ```
- **Простыми словами:** Это как «пропуск в клуб». Правило одно: «Если хочешь обрабатывать запросы, реализуй метод `ServeHTTP`». Всё, что имеет этот метод, автоматически становится валидным обработчиком для сервера.
- **Как работает под капотом:**
  Когда клиент стучится на сервер, `net/http` находит подходящий `Handler` и вызывает у него `ServeHTTP(w, r)`. Вы **не вызываете этот метод вручную** — это делает внутренний цикл сервера.
- **Пример структуры-обработчика:**
  ```go
  type HealthHandler struct{}

  func (h HealthHandler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
      w.Header().Set("Content-Type", "application/json")
      w.Write([]byte(`{"status":"ok"}`))
  }
  ```

---

## 🔄 2. `http.HandlerFunc` — «Адаптер для обычных функций»
- **Проблема:** Писать отдельные структуры для каждого маршрута неудобно. Чаще всего хочется просто функцию: `func(w http.ResponseWriter, r *http.Request)`.
- **Решение:** `http.HandlerFunc` — это специальный тип-функция, который «притворяется`http.Handler`:
  ```go
  type HandlerFunc func(http.ResponseWriter, *http.Request)

  func (f HandlerFunc) ServeHTTP(w http.ResponseWriter, r *http.Request) {
      f(w, r) // Магия: тип вызывает саму себя!
  }
  ```
- **Простыми словами:** Это «волшебная обёртка». Вы пишете обычную функцию, а Go автоматически добавляет ей метод `ServeHTTP`, чтобы она подошла под интерфейс `Handler`.
- **Пример использования:**
  ```go
  func usersHandler(w http.ResponseWriter, r *http.Request) {
      w.Write([]byte("Список пользователей"))
  }

  // Превращаем функцию в Handler:
  var handler http.Handler = http.HandlerFunc(usersHandler)
  ```

---

## 🤝 3. Как они работают вместе: магия `http.HandleFunc`
- В стандартной библиотеке есть удобная функция для регистрации маршрутов:
  ```go
  http.HandleFunc("/users", usersHandler)
  ```
- **Что происходит внутри:**
    1. Вы передаёте обычную функцию `usersHandler`.
    2. `HandleFunc` автоматически оборачивает её: `http.HandlerFunc(usersHandler)`.
    3. Полученный объект кладётся во внутренний роутер (`http.DefaultServeMux`).
- **Итог:** Вы пишете простую функцию, а Go сам делает её совместимой с `http.Handler`. Вам не нужно вручную создавать типы или методы.

---

## 🧩 4. Почему эта архитектура гениальна для Go
- ✅ **Единый стандарт:** Все сторонние роутеры (`chi`, `mux`), middleware и фреймворки работают с `http.Handler`. Вы можете менять компоненты как Lego-кубики.
- ✅ **Middleware — это просто:** Промежуточное ПО — это функция, которая принимает `http.Handler`, создаёт новый `http.Handler` и возвращает его.
  ```go
  func loggingMiddleware(next http.Handler) http.Handler {
      return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
          log.Printf("%s %s", r.Method, r.URL.Path)
          next.ServeHTTP(w, r) // Передаём управление следующему в цепочке
      })
  }
  ```
- ✅ **Тестируемость:** Можно передать любой `Handler` в `httptest.NewRecorder()` и проверить ответ без запуска реального порта.

## 💡 5. Важные моменты для изучения (под капотом и в бою)
| Момент | Почему это важно | Как запомнить |
|--------|------------------|---------------|
| 🔑 **Один запрос = одна горутина** | Сервер автоматически запускает `ServeHTTP` в отдельной горутине. Не нужно писать `go handler.ServeHTTP(...)`. | «Go сам раздаёт потоки. Ваша задача — только логика внутри». |
| ⚠️ **`WriteHeader` вызывается один раз** | После первого `w.WriteHeader()` или записи тела ответа заголовки «улетают» клиенту. Менять их потом бесполезно. | «Заголовки → тело. Назад пути нет». |
| 📦 **`HandlerFunc` vs `HandleFunc`** | `HandlerFunc` (большая `F`) — тип-адаптер. `HandleFunc` (маленькая `f`) — функция регистрации маршрута. | «Func с большой буквы — тип, с маленькой — действие». |
| 🚫 **Не блокируйте `ServeHTTP`** | Долгие синхронные операции занимают горутину и соединение. Сервер исчерпает лимит подключений. | «Обработал → отдал управление. Тяжёлую работу — в фон/очередь». |
| ✅ **Всегда закрывайте `r.Body`** | Даже если не читаете тело запроса. Иначе возможна утечка памяти в пуле соединений. | «`defer r.Body.Close()` — первая строка в хендлере». |

# 🔍 Модуль 1, Пункт 3: Стандартный маршрутизатор `http.ServeMux`
> *Простыми словами: как направить запрос по правильному адресу, не подключая тяжелые библиотеки и не тонуть в конфигурации*

---

## 📌 1. Что такое `http.ServeMux` и как он работает (базово)
- **Простыми словами:** Это «сортировщик» на почте. Когда приходит письмо (HTTP-запрос), `ServeMux` смотрит на конверт (URL и метод) и кладёт его в нужный ящик (вызывает нужный обработчик).
- **Как создать свой роутер:**
  ```go
  mux := http.NewServeMux() // Создаём локальный экземпляр
  mux.HandleFunc("/health", healthHandler)
  mux.HandleFunc("/users", usersHandler)
  ```
- **Почему лучше не использовать `http.DefaultServeMux`:**
    - `DefaultServeMux` — глобальная переменная. Если её использовать, все тесты и части приложения будут «мешать» друг другу.
    - Свой `mux` изолирован, его легко передать в тесты, подменить или запустить несколько серверов параллельно.
      ✅ **Правило:** Всегда создавайте `http.NewServeMux()` явно.

## 🚀 2. Революция Go 1.22+: методы, параметры, wildcard
До версии 1.22 роутер умел только сравнивать пути. Теперь он понимает современный REST без сторонних библиотек.

| Возможность | Синтаксис | Что делает |
|-------------|-----------|------------|
| **Метод-специфичный маршрут** | `"GET /users"` | Отвечает только на `GET`. На `POST` вернёт `405 Method Not Allowed` |
| **Параметр в пути** | `"GET /users/{id}"` | Ловит динамический кусок пути. `{id}` может быть числом, UUID, строкой |
| **Wildcard (остаток пути)** | `"GET /files/{path...}"` | Забирает всё, что идёт после `/files/`, включая слэши. Идеально для статических файлов или вложенных ресурсов |

👉 *Простыми словами:* Раньше роутер видел только улицу (`/users`). Теперь он видит и направление (`GET`), и номер дома (`{id}`), и даже подъезд/этаж (`{path...}`).

## 🎯 3. Правила сопоставления паттернов (приоритеты)
`ServeMux` не просто ищет первое совпадение. Он выбирает **самый точный** паттерн по строгим правилам:

1. 🔝 **Точное совпадение** (`GET /users/profile`) — всегда побеждает.
2. 🔽 **Метод + полный путь** (`POST /users`) — выше, чем просто путь.
3. 📏 **Длина пути** — чем длиннее и конкретнее шаблон, тем выше приоритет.
4. 🌐 **Wildcard** (`/api/{rest...}`) — самый низкий приоритет, работает как «ловушка» для всего остального.

⚠️ **Важно:** Если вы зарегистрируете конфликтующие паттерны (например, `"GET /users"` и `"POST /users"`), Go **вызовет панику при старте сервера**. Это фича, а не баг: лучше узнать об ошибке до деплоя, чем ловить странные ответы в production.

## 📦 4. Извлечение параметров пути (`r.PathValue`)
В Go 1.22 параметры больше не нужно парсить регулярками или `strings.Split`. Они уже ждут вас в `http.Request`.

```go
func getUserHandler(w http.ResponseWriter, r *http.Request) {
    // 1. Достаём параметр как строку
    idStr := r.PathValue("id") 
    
    // 2. Проверяем, что он есть (на случай изменений в маршрутах)
    if idStr == "" {
        http.Error(w, "missing id", http.StatusBadRequest)
        return
    }

    // 3. Конвертируем в нужный тип
    id, err := strconv.Atoi(idStr)
    if err != nil {
        http.Error(w, "id must be a number", http.StatusBadRequest)
        return
    }

    // 4. Используем
    fmt.Fprintf(w, "Запрошен пользователь с ID: %d", id)
}
```
👉 *Простыми словами:* `PathValue` — это «кармашек» в запросе, куда роутер уже положил вырезанный кусок пути. Ваша задача только достать и проверить формат.

## ⚖️ 5. Когда `ServeMux` достаточно, а когда нужен сторонний роутер
| Сценарий | Рекомендуемый инструмент | Почему |
|----------|--------------------------|--------|
| Микросервис на 5-15 маршрутов | `http.ServeMux` | Лёгкий, в стандартной библиотеке, быстрый, не ломает `net/http` контракты |
| Простое REST API без сложной логики | `http.ServeMux` | Поддерживает методы, параметры, группы через префиксы |
| 50+ маршрутов, вложенные группы, автослэш | `chi` / `echo` | Удобная группировка `v1.Group()`, автоматическая нормализация URL, встроенные middleware-цепочки |
| Нужны регулярные выражения в путях | `gorilla/mux` (устарел) или `chi` | `ServeMux` не поддерживает regex |
| Миграция старого legacy-кода | `chi` или `gin` | Помогут плавно перейти без переписывания всей архитектуры |

✅ **Вывод:** Начинайте всегда со `ServeMux`. Переходите на внешний роутер только когда почувствуете боль от ручного префиксинга или нехватки группировки.

## 💡 6. Важные моменты для изучения (чек-лист)

|--------|------------------|---------------|
| 🔒 **Паника при конфликтах** | `ServeMux` проверяет маршруты при регистрации, а не при запросе | «Ошибки маршрутов ловятся на старте, а не в бою» |
| 📝 **Регистр имеет значение** | `/Users` ≠ `/users` | «URL чувствителен к регистру. Пишите в нижнем регистре» |

| 🔍 `r.Pattern()` | Возвращает строку паттерна, который сработал (полезно для логов) | «Логируйте `r.Pattern()`, чтобы видеть, какой маршрут сработал» |
| 🧩 **Группировка префиксами** | `mux.Handle("/api/v1/", http.StripPrefix("/api/v1", v1Mux))` | «Вложенные роутеры собираются через `StripPrefix` или `http.NewServeMux()` с префиксом» |

#### 4. Работа с `http.Request` и `http.ResponseWriter`
- **`http.Request`** — всё, что прислал клиент:
  - `r.URL`, `r.Method`, `r.Header`, `r.Body`, `r.Context()`

- **`http.ResponseWriter`** — через него отправляем ответ:
  - `w.WriteHeader(200)` — статус-код
  - `w.Header().Set("Content-Type", "application/json")` — заголовки
  - `fmt.Fprint(w, "тело")` или `json.NewEncoder(w).Encode(obj)` — тело ответа
  > ⚠️ **Важно:** после вызова `WriteHeader()` или записи тела менять заголовки уже нельзя!

# 🔍 Модуль 1, Пункт 4: Работа с `http.Request` и `http.ResponseWriter`
> *Простыми словами: как правильно «распаковать» то, что прислал клиент, и «упаковать» ответ, не нарушив протокол и не утекши память*

## 📥 1. `http.Request` — «Конверт с данными от клиента»
- **Что это:** Структура, в которую `net/http` автоматически собирает всё, что прислал клиент: метод, URL, заголовки, тело запроса и контекст.
- **Ключевые поля и методы:**
  | Поле/Метод | Что внутри | Как использовать |
  |------------|------------|------------------|
  | `r.Method` | `GET`, `POST`, `PUT` и т.д. | `if r.Method != http.MethodPost { ... }` |
  | `r.URL.Path` | Путь без параметров: `/users` | `if r.URL.Path == "/health" { ... }` |
  | `r.URL.Query()` | Карта параметров: `?page=1&limit=20` | `r.URL.Query().Get("page")` → `"1"` |
  | `r.Header` | HTTP-заголовки | `r.Header.Get("Authorization")` |
  | `r.Body` | Поток с телом запроса (JSON, файлы, форма) | `json.NewDecoder(r.Body).Decode(&obj)` |
  | `r.Context()` | Контекст запроса (отмена, таймауты, ID) | Передавайте в БД/внешние вызовы: `db.QueryContext(r.Context(), ...)` |

- **⚠️ Главное правило тела запроса:** `r.Body` — это **поток (stream)**. Его можно прочитать только **один раз**. После чтения его **обязательно** нужно закрыть, иначе соединение «зависнет» и память утечёт.
  ```go
  defer r.Body.Close() // Ставьте сразу после проверки, что тело не nil
  ```

---

## 📤 2. `http.ResponseWriter` — «Ваш ответ клиенту»
- **Что это:** Интерфейс, через который вы формирует и отправляете HTTP-ответ. Не структура, а именно интерфейс с тремя методами.
- **Ключевые методы:**
  ```go
  w.Header().Set("Content-Type", "application/json") // 1. Заголовки
  w.WriteHeader(http.StatusCreated)                  // 2. Статус-код
  w.Write([]byte(`{"id":1}`))                        // 3. Тело ответа
  ```
- **Удобные обёртки от стандартной библиотеки:**
    - `http.Error(w, "bad request", http.StatusBadRequest)` → сразу ставит статус, заголовок `text/plain` и пишет тело.
    - `json.NewEncoder(w).Encode(data)` → автоматически ставит `Content-Type: application/json` (иногда) и пишет тело. **Рекомендуется** для JSON API.

---

## ⚖️ 3. Жёсткие правила порядка записи ответа
В HTTP заголовки и статус отправляются **до** тела. Go строго следит за этим:

1. ✅ **Сначала заголовки:** `w.Header().Set(...)`
2. ✅ **Потом статус:** `w.WriteHeader(201)`
3. ✅ **Потом тело:** `w.Write(...)` или `json.NewEncoder(w).Encode(...)`

🔴 **Что будет, если нарушить порядок?**
- Если вызвать `w.Write()` или `json.Encode()` до `w.WriteHeader()`, Go **автоматически** отправит статус `200 OK`. Изменить его потом будет невозможно.
- Если вызвать `w.WriteHeader()` после записи тела → сервер проигнорирует ваш статус, запишет в лог предупреждение: `http: superfluous response.WriteHeader call`.

👉 *Простыми словами:* «Сначала наклейте марки и поставьте печать (заголовки + статус), потом положите письмо в конверт (тело). Наоборот не получится».

## 💡 4. Важные моменты для изучения (чек-лист)
| Момент | Почему это важно | Как запомнить |
|--------|------------------|---------------|
| 🔒 `r.Body` читается 1 раз | Это сеть, а не переменная в памяти. Повторный вызов вернёт пустоту | «Съел → закрыл → забыл» |
| 🛑 `defer r.Body.Close()` | Без этого пул соединений `net/http` не освободит ресурсы → утечка памяти | «Первая строка в хендлере после проверки на nil» |
| 📏 Ограничение размера тела | Злоумышленник может прислать 10 ГБ JSON и «задушить» сервер | `r.Body = http.MaxBytesReader(w, r.Body, 1<<20)` (1 МБ) |
| 🔁 `w.Header()` возвращает карту | Изменения применяются только до первого `Write`/`WriteHeader` | «Заголовки фиксируются на лету. После отправки — поздно» |
| 🌐 `r.Context()` = кнопка «Стоп» | Если клиент отключился, контекст отменится. БД/внешний вызов прервётся | «Всегда передавайте `r.Context()` вниз по цепочке» |
| 📦 `json.Encoder` vs `json.Marshal` | `Encoder` пишет сразу в `w` без промежуточного `[]byte` → меньше память | «Для ответов в HTTP всегда `json.NewEncoder(w)`» |

#### 5. Graceful shutdown (корректное завершение)
- Зачем? Чтобы при перезапуске сервер не обрывал текущие запросы.
- Как работает:
  1. Ловим сигнал `SIGINT`/`SIGTERM` через `signal.Notify`
  2. Создаём `context.WithTimeout` на 10-30 секунд
  3. Вызываем `server.Shutdown(ctx)` — сервер перестаёт принимать новые запросы, но дожидается завершения текущих
- **Простыми словами:** «Не выключай свет, пока все не вышли из комнаты».

# 🔍 Модуль 1, Пункт 5: Graceful shutdown через `context` и `signal.Notify`
> *Простыми словами: как выключить сервер так, чтобы текущие запросы доделали работу, а клиенты не получили «соединение сброшено»*

---

## 📌 1. Что такое Graceful Shutdown и зачем он нужен
- **Проблема:** Если остановить Go-программу через `Ctrl+C` или `docker stop`, процесс завершится мгновенно. Все активные HTTP-запросы оборвутся на полпути. Клиенты получат ошибки, транзакции в БД могут остаться «подвешенными», а балансировщики нагрузки будут ещё пару секунд слать трафик на уже мёртвый инстанс.
- **Решение:** Graceful Shutdown («мягкая остановка») говорит серверу:
    1. Перестать принимать новые соединения.
    2. Дождаться завершения текущих запросов.
    3. Корректно закрыть БД, кеш, файлы.
    4. Завершить процесс.
- **Аналогия:** Ресторан закрывается в 22:00. Официанты перестают сажать новых гостей, но доедают обслуживание тех, кто уже за столом. Только когда зал пуст → гасят свет и закрывают дверь.

---

## 🔄 2. Как это работает: пошаговый алгоритм
1. **Ловим сигнал ОС:** ОС отправляет процессу сигнал при остановке:
    - `SIGINT` → `Ctrl+C` в терминале
    - `SIGTERM` → `docker stop`, `kubectl delete pod`, облачные провайдеры
2. **Создаём контекст с таймаутом:** Чтобы сервер не висел вечно, если какой-то запрос «завис».
3. **Вызываем `srv.Shutdown(ctx)`:**
    - Закрывает listening-сокет (новые запросы сразу получают ошибку).
    - Ждёт, пока активные горутины хендлеров вернут ответ.
    - Если время в `ctx` вышло → принудительно завершает работу.
4. **Освобождаем ресурсы:** Закрываем пул БД, воркеры, очереди.
5. **Выходим из `main()`:** Программа завершается с кодом `0`.

---

## 🛠 3. Код на практике (шаблон для production)
```go
package main

import (
    "context"
    "log"
    "net/http"
    "os"
    "os/signal"
    "syscall"
    "time"
)

func main() {
    // 1. Создаём контекст, который отменится при SIGINT или SIGTERM
    ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt, syscall.SIGTERM)
    defer stop()

    mux := http.NewServeMux()
    mux.HandleFunc("/health", func(w http.ResponseWriter, r *http.Request) {
        w.Write([]byte("OK"))
    })

    srv := &http.Server{
        Addr:         ":8080",
        Handler:      mux,
        ReadTimeout:  5 * time.Second,
        WriteTimeout: 10 * time.Second,
        IdleTimeout:  60 * time.Second,
    }

    // 2. Запускаем сервер в отдельной горутине
    go func() {
        log.Println("Сервер запущен на :8080")
        if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
            log.Fatalf("Ошибка запуска сервера: %v", err)
        }
    }()

    // 3. Ждём сигнал завершения (блокируем main goroutine)
    <-ctx.Done()
    log.Println("Получен сигнал остановки. Запускаем graceful shutdown...")

    // 4. Контекст с таймаутом на "дожатие" текущих запросов
    shutdownCtx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
    defer cancel()

    // 5. Мягкая остановка HTTP-сервера
    if err := srv.Shutdown(shutdownCtx); err != nil {
        log.Fatalf("Сервер не успел завершиться: %v", err)
    }

    log.Println("Сервер корректно остановлен. Можно закрывать БД и выходить.")
    // Здесь: db.Close(), redis.Close(), и т.д.
}
```

## 💡 4. Важные моменты для изучения (чек-лист)
| Момент | Почему это важно | Как запомнить |
|--------|------------------|---------------|
| 🔔 `signal.NotifyContext` | Современный аналог `signal.Notify + channel`. Чище, не требует ручного `close(chan)` | «Один вызов → контекст → готово» |
| ⏱ Таймаут в `Shutdown()` | Без него сервер может висеть вечно, если клиент «отвалился» по сети | «Всегда ставьте 10-30 сек. Лучше завершиться, чем висеть» |
| 🚫 `SIGKILL` (`kill -9`) | Обходит graceful shutdown на уровне ядра ОС. Процесс умирает мгновенно | «Graceful работает только для `SIGINT`/`SIGTERM`» |
| 📉 Новые запросы при shutdown | Сразу получают `connection refused` или `503`. Не обрабатываются | «Сервер «закрывает дверь», но обслуживает тех, кто уже внутри» |
| 🧹 Ресурсы после shutdown | БД, пулы, файлы нужно закрывать **ПОСЛЕ** `srv.Shutdown()`, иначе хендлеры упадут | «Сначала HTTP → потом БД → потом выход» |
| 🔄 `http.ErrServerClosed` | Возвращается `srv.ListenAndServe()` при graceful shutdown. Это **не ошибка** | `if err != nil && err != http.ErrServerClosed { log.Fatal(err) }` |

# 🔍 Модуль 1, Пункт 6: Базовая обработка ошибок и возврат статус-кодов
> *Простыми словами: как не «глотать» сбои, возвращать клиенту понятные сообщения и не ломать сервер из-за пустяков*

---

## 📌 1. Зачем нужна обработка ошибок в вебе?
- **Проблема:** В реальном мире ошибки неизбежны: клиент прислал битый JSON, пользователь не найден в БД, диск заполнился, внешний сервис упал. Если игнорировать `err != nil`, сервер либо молча вернёт пустой ответ, либо упадёт с `panic`.
- **Решение:**
    1. **Ловим ошибку** сразу там, где она возникла.
    2. **Логируем детали** для разработчика (стек, `request_id`, исходная причина).
    3. **Возвращаем клиенту безопасное сообщение** + правильный HTTP-статус.
- **Аналогия:** Кассир в магазине. Если товар не сканируется, он не кричит в зале о поломке сканера (это для техников). Он спокойно говорит покупателю: «Извините, попробуйте другой способ оплаты» (понятный статус).

---

## 🚦 2. HTTP статус-коды: когда какой возвращать?
Статус-код — это «светофор» для клиента. Он говорит, кто виноват и что делать дальше.

| Диапазон | Значение | Когда использовать | Пример |
|----------|----------|-------------------|--------|
| `2xx` | Успех | Запрос выполнен | `200 OK`, `201 Created` (после POST), `204 No Content` (после DELETE) |
| `4xx` | Ошибка клиента | Клиент прислал неверные данные или не имеет прав | `400 Bad Request`, `401 Unauthorized`, `403 Forbidden`, `404 Not Found`, `409 Conflict` |
| `5xx` | Ошибка сервера | Сломалось у вас (БД, паника, внешний API) | `500 Internal Server Error`, `503 Service Unavailable` |

👉 *Простыми словами:*
- `4xx` → «Ты свернул не туда, проверь запрос».
- `5xx` → «У нас авария, мы уже чиним».
- Никогда не возвращайте `200` с телом `{"error": "..."}`. Это ломает стандартные HTTP-клиенты и балансировщики.

---

## 🛠 3. Паттерны обработки ошибок в Go
### 🔹 Паттерн 1: Ранний возврат (Early Return)
Самый идиоматичный способ в Go. Не пишите `else`, выходите сразу при ошибке.
```go
func createUser(w http.ResponseWriter, r *http.Request) {
    var req User
    if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
        // 1. Логируем для себя
        log.Printf("decode error: %v", err)
        // 2. Отвечаем клиенту
        http.Error(w, "invalid JSON", http.StatusBadRequest)
        return
    }
    // Дальше работаем с req, зная что он валиден
}
```

### 🔹 Паттерн 2: JSON-обёртка вместо `http.Error`
`http.Error` возвращает `text/plain`. Для REST API это плохо. Лучше сразу писать JSON:
```go
func respondError(w http.ResponseWriter, msg string, status int) {
    w.Header().Set("Content-Type", "application/json")
    w.WriteHeader(status)
    json.NewEncoder(w).Encode(map[string]string{"error": msg})
}
// Использование:
respondError(w, "user not found", http.StatusNotFound)
```

### 🔹 Паттерн 3: Маппинг ошибок БД на статус-коды
Не все ошибки = `500`. `sql.ErrNoRows` — это `404`, нарушение уникальности — `409`.
```go
err := repo.GetUser(ctx, id)
if errors.Is(err, sql.ErrNoRows) {
    respondError(w, "user not found", http.StatusNotFound)
    return
}
if err != nil {
    // Остальные ошибки — вина сервера
    log.Printf("db error: %v", err)
    respondError(w, "internal server error", http.StatusInternalServerError)
    return
}
```

## 💡 4. Важные моменты для изучения (чек-лист)
| Момент | Почему это важно | Как запомнить |
|--------|------------------|---------------|
| 📝 `http.Error` → `text/plain` | Фронтенд и API-шлюзы ожидают JSON. `http.Error` удобен только для отладки | «В production пишите JSON-ошибки вручную или через helper» |
| 🔍 `errors.Is` / `errors.As` | С Go 1.13 ошибки можно оборачивать: `fmt.Errorf("ctx: %w", err)`. `errors.Is` найдёт причину в цепочке | «Сравнивайте по смыслу, а не по тексту ошибки» |
| 🚫 Не логируйте детали клиенту | `panic: index out of range` или `password field too long` = информация для атакующего | «В лог — всё. Клиенту — безопасно и обобщённо» |
| 📉 `500` ≠ всегда падение | `500` — это сигнал для мониторинга. Если ошибок много → алерт в Slack/PagerDuty | «`500` = вызовем дежурного инженера» |
| 🔄 Единый формат ошибки | `{ "error": "message", "code": "USER_NOT_FOUND" }` упрощает работу фронтенда | «Договоритесь о формате в команде и используйте его везде» |
| ⚠️ Ошибки после `WriteHeader` | Если уже записали статус/тело, `http.Error` или `respondError` **не сработают** | «Сначала решите, какой статус вернуть. Потом пишите» |

## ✅ 5. Мини-практика (закрепление)
1. Создайте хендлер `GET /users/{id}`, который имитирует работу с БД:
    - Если `id == "1"` → вернуть JSON пользователя (`200`)
    - Если `id == "0"` → вернуть ошибку «user not found» (`404`)
    - Если `id` не число → вернуть «invalid ID format» (`400`)
    - В остальных случаях → симулировать сбой БД (`500`)
2. Напишите функцию `respondError(w, msg, status)` в формате JSON.
3. Добавьте логирование: `log.Printf("[%s] %s: %v", r.Method, r.URL.Path, err)` только для `5xx`.
4. Протестируйте все сценарии через `curl -v`:
   ```bash
   curl -v http://localhost:8080/users/1
   curl -v http://localhost:8080/users/0
   curl -v http://localhost:8080/users/abc
   curl -v http://localhost:8080/users/999
   ```
5. Убедитесь, что в консоли сервера логируются только `5xx`, а клиент всегда получает валидный JSON.
