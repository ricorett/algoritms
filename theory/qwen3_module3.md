## 📚 Подробный разбор тем

### 1. `database/sql` и пул соединений
- **Простыми словами:** `database/sql` — это стандартная библиотека Go для работы с БД. Она не подключается к базе напрямую, а управляет «бассейном» (пулом) открытых соединений. Когда вам нужен запрос, она берёт свободное соединение из пула, выполняет запрос и возвращает его обратно в пул.
- **Ключевые моменты:**
  - `sql.Open()` → только проверяет формат строки подключения, **не создаёт соединение сразу**.
  - `db.Ping()` или `db.PingContext()` → реальная проверка: может ли приложение достучаться до БД.
  - **Настройки пула (обязательно):**
    - `SetMaxOpenConns(n)` → максимальное число одновременных соединений (без лимита = риск «убить» БД под нагрузкой)
    - `SetMaxIdleConns(n)` → сколько соединений держать «в тепле» для повторного использования
    - `SetConnMaxLifetime(duration)` → как долго соединение живёт перед пересозданием (защита от «зависших» или протухших соединений на стороне БД)
  - ⚠️ **Важно:** `sql.DB` — это глобальный объект. Создавайте его **один раз** при старте приложения. Никогда не закрывайте его после каждого запроса. Закрывают только при graceful shutdown.

### 2. Prepared Statements и Транзакции
- **Prepared Statements (Подготовленные выражения):**
  - **Простыми словами:** Вы сначала «готовите» шаблон запроса в БД, а потом подставляете в него данные. Это быстрее и на 100% защищает от SQL-инъекций.
  - В Go: `db.QueryContext(ctx, "SELECT * FROM users WHERE id = $1", id)` → драйвер сам подготовит и безопасно подставит `$1`.
  - ✅ **Правило:** Никогда не склеивайте пользовательские данные в SQL через `fmt.Sprintf` или `+`. Всегда используйте параметры (`$1`, `?` в зависимости от драйвера).
- **Транзакции:**
  - **Простыми словами:** Группа операций, которые либо выполняются все, либо не выполняется ни одна. Пример: перевод денег (списали у одного → добавили другому). Если на втором шаге ошибка → откатываем первый.
  - Как работает: `tx, err := db.Begin()` → `tx.Exec(...)` → `tx.Commit()` или `tx.Rollback()`.
  - ⚠️ **Важно:** Всегда используйте `defer tx.Rollback()`. Если `Commit()` пройдёт успешно, `Rollback()` безопасно ничего не сделает. Если код упадёт раньше — откатит изменения. Это спасает от «зависших» транзакций и блокировок.

### 3. Паттерн Repository / DAO
- **Простыми словами:** Слой между вашим кодом и базой данных. Хендлеры не знают про SQL. Они говорят репозиторию: «Дай мне пользователя с ID=5». Репозиторий идёт в БД, достаёт, преобразует в Go-структуру и отдаёт обратно.
- **Зачем нужен:**
  - Изолирует SQL от бизнес-логики (хендлеры становятся чище)
  - Позволяет легко подменить БД на моки в тестах
  - Упрощает поддержку: SQL-запросы лежат в одном месте
- **Как выглядит:**
  ```go
  type UserRepository interface {
      GetByID(ctx context.Context, id int) (*User, error)
      Create(ctx context.Context, u *User) error
  }
  type postgresRepo struct { db *sql.DB }
  func (r *postgresRepo) GetByID(ctx context.Context, id int) (*User, error) { ... }
  ```
- ✅ **Важно:** Передавайте `context.Context` во **все** методы репозитория. Это позволит отменять долгие запросы, если клиент отключился.

### 4. Миграции (`pressly/goose` или `golang-migrate`)
- **Простыми словами:** Миграции — это «версионный контроль» для структуры вашей базы данных. Как Git для кода, но для таблиц, колонок и индексов.
- **Как работает:**
  - Создаёте файлы: `001_create_users.up.sql`, `001_create_users.down.sql`
  - Запускаете команду → она читает внутреннюю таблицу `schema_migrations`, видит, какие уже применены, и выполняет только новые.
  - `up` → применяет изменения, `down` → откатывает.
- **Почему важно:**
  - На разных серверах (dev, staging, prod) база всегда в одном состоянии.
  - Можно безопасно обновлять схему без ручного запуска SQL-скриптов в консоли.
- ⚠️ **Важно:** Миграции выполняются строго по порядку. Никогда не меняйте уже применённые файлы — создавайте новые. `down` должен быть зеркальным отражением `up`.

### 5. N+1 проблема, батчинг и индексация (базово)
- **N+1 проблема:**
  - **Простыми словами:** Вы делаете 1 запрос, чтобы получить список записей, а потом в цикле делаете ещё N запросов для каждой записи. Например: получить 100 постов → потом 100 запросов, чтобы получить автора каждого поста.
  - ✅ **Решение:** `JOIN` в SQL или `WHERE id IN (...)`. Один запрос вместо 101.
- **Батчинг (пакетная обработка):**
  - Вставлять/обновлять много строк за один запрос: `INSERT INTO users (name, email) VALUES ($1, $2), ($3, $4), ...`
  - ⚡ В 10-100 раз быстрее, чем цикл с `INSERT`. В Go можно использовать `pgx` или собирать батчи вручную.
- **Индексация:**
  - **Простыми словами:** Индекс — это «оглавление» книги. Без него БД читает все строки подряд (FULL SCAN). С индексом — сразу находит нужную.
  - Создавайте индексы на полях, по которым часто ищете или сортируете (`WHERE user_id = ...`, `ORDER BY created_at`).
  - ⚠️ Не создавайте индексы на всё подряд: они замедляют `INSERT`/`UPDATE` и занимают место.

### 6. Mocking БД для тестов (`sqlmock`)
- **Простыми словами:** `sqlmock` — это «фейковая» база данных, которая живёт только в памяти теста. Вы говорите ему: «Если пришлют запрос `SELECT...`, верни вот такие данные». Не нужно поднимать реальный PostgreSQL для каждого unit-теста.
- **Как работает:**
  ```go
  db, mock, err := sqlmock.New()
  defer db.Close()
  mock.ExpectQuery("SELECT id, name FROM users WHERE id = \\$1").
      WithArgs(1).
      WillReturnRows(sqlmock.NewRows([]string{"id", "name"}).AddRow(1, "Alice"))
  ```
- ✅ **Важно:** Тесты с `sqlmock` проверяют, что ваш код формирует правильные SQL-запросы и правильно обрабатывает ответы. Они не проверяют реальную работу БД (для этого нужны интеграционные тесты с Docker).
- ⚠️ **Важно:** Всегда в конце теста вызывайте `mock.ExpectationsWereMet()`. Иначе тест может пройти успешно, хотя ожидание не совпало или запрос не ушёл.

## 🛠 Практика (пошагово)

1. **Подключение PostgreSQL**
   - Поднимите БД через Docker: `docker run -e POSTGRES_PASSWORD=secret -p 5432:5432 postgres:16`
   - Инициализируйте `database/sql`, настройте пул соединений, вызовите `Ping()`
   - Оберните `*sql.DB` в структуру `Database`, чтобы не передавать её как голый указатель

2. **Миграции через `goose`**
   - Установите: `go install github.com/pressly/goose/v3/cmd/goose@latest`
   - Создайте миграцию: `goose create create_users sql`
   - Напишите `CREATE TABLE` в `.up.sql`, `DROP TABLE` в `.down.sql`
   - Примените: `goose postgres "postgres://..." up`

3. **Repository + CRUD**
   - Создайте интерфейс `UserRepository` и реализацию `postgresRepo`
   - Реализуйте `Create`, `GetByID`, `List`, `Update`, `Delete`
   - Используйте `QueryContext` / `ExecContext`, обрабатывайте `sql.ErrNoRows` (это значит «не найдено», а не «ошибка сервера»)

4. **Транзакции**
   - Напишите метод `UpdateUserWithProfile` или `TransferBalance`
   - Реализуйте через `db.Begin()`, `defer tx.Rollback()`, `tx.Commit()`
   - Протестируйте сценарий с намеренной ошибкой → убедитесь, что данные откатились

5. **Тесты с `sqlmock`**
   - Напишите unit-тест для `GetByID`
   - Настройте ожидание запроса, верните фейковые строки
   - Проверьте, что метод вернул правильную структуру и `nil` ошибку

✅ **Чек-лист завершения модуля:**
- [ ] БД подключена, пул настроен (`MaxOpenConns`, `MaxIdleConns`, `ConnMaxLifetime`), `Ping()` проходит
- [ ] Миграции создаются, применяются и откатываются одной командой
- [ ] CRUD работает через Repository, SQL-запросы вынесены из хендлеров
- [ ] Транзакции корректно коммитят или откатываются при ошибках (`defer Rollback`)
- [ ] Решена проблема N+1 (через `JOIN` или `IN`)
- [ ] Unit-тесты репозитория проходят с `sqlmock`
- [ ] Все запросы используют `context.Context` и обрабатывают `sql.ErrNoRows`
