## 📚 Подробный разбор тем

### 1. Хеширование паролей (`bcrypt`)
- **Простыми словами:** Пароли нельзя хранить как обычный текст. Если базу данных украдут, все аккаунты станут уязвимы. Хеширование превращает пароль в «необратимую кашу»: даже зная результат, невозможно восстановить исходный пароль.
- **Как работает:** `bcrypt` добавляет к паролю случайную «соль» и многократно пропускает его через криптографическую функцию. Это делает перебор (brute-force) очень медленным и дорогим для атакующего.
- **Важные моменты для изучения:**
  - ✅ **Никогда не используйте MD5/SHA1 для паролей.** Только `bcrypt`, `argon2` или `scrypt`.
  - ✅ **Настраивайте `cost` (стоимость вычислений).** Значение по умолчанию `10` или `12`. Меньше = легко взломать, больше = сервер будет «тормозить» при каждом логине.
  - ✅ **Проверка пароля:** используйте только `bcrypt.CompareHashAndPassword()`. Никогда не сравнивайте строки напрямую и не пытайтесь «расхешировать» пароль.

### 2. JWT (JSON Web Tokens)
- **Простыми словами:** JWT — это цифровой пропуск в формате JSON. Сервер подписывает его секретным ключом. Клиент сохраняет токен и прикрепляет к каждому запросу. Сервер проверяет подпись и решает: пускать или нет.
- **Структура:** `Header.Algorithm.Payload.Signature`. В `Payload` кладут `user_id`, `exp` (время жизни), `role`. **Не кладите туда пароли или чувствительные данные!**
- **Важные моменты для изучения:**
  - ✅ JWT **не шифруется**, только подписывается. Любой, кто перехватит токен, увидит его содержимое. Используйте HTTPS!
  - ✅ Всегда проверяйте `exp` (время истечения). Просроченные токены должны сразу отклоняться.
  - ✅ Для монолитов подходит `HS256` (один общий секрет). Для микросервисов лучше `RS256` (публичный ключ для проверки, приватный для подписи).
  - ⚠️ JWT нельзя отозвать мгновенно. Если токен украден, он работает до истечения срока. Решение: короткий срок жизни (10-15 мин) + Refresh Token.

### 3. Refresh Token Flow
- **Простыми словами:** Чтобы не заставлять пользователя вводить пароль каждые 15 минут, выдаём два токена: `access` (короткоживущий, для запросов) и `refresh` (долгоживущий, только для получения нового `access`).
- **Как работает:**
  1. Клиент логинится → получает `access_token` (15 мин) и `refresh_token` (30 дней).
  2. `access_token` истёк → клиент отправляет `refresh_token` на `/auth/refresh` → получает новую пару.
  3. При компрометации `refresh_token` можно отозвать (хранить хеши в БД или blacklist).
- **Важные моменты для изучения:**
  - ✅ Храните `refresh_token` в `HTTP-only Secure Cookie` (для веба) или в защищённом хранилище (для мобильных). **Не в `localStorage`** (уязвимо к XSS).
  - ✅ Всегда генерируйте новый `refresh_token` при каждом обновлении (rotation). Старый аннулируйте.
  - ✅ При смене пароля или выходе из системы — инвалидируйте все refresh-токены пользователя в БД/Redis.

### 4. OAuth2 / OpenID Connect (базово)
- **Простыми словами:** «Войти через Google/GitHub». Вы делегируете проверку личности крупному провайдеру, а он возвращает вам подтверждение, что пользователь действительно существует.
- **Как работает в Go:** `golang.org/x/oauth2`. Вы перенаправляете пользователя на провайдера → он возвращается с `code` → ваш бэкенд обменивает `code` на `token` → получает профиль.
- **Важные моменты для изучения:**
  - ✅ Никогда не храните `client_secret` на фронтенде. Обмен `code → token` всегда происходит на бэкенде.
  - ✅ Всегда проверяйте `state` параметр при возврате от провайдера. Это защита от CSRF-атак во время авторизации.
  - ✅ OpenID Connect = OAuth2 + слой идентификации. Он стандартизирует получение `id_token` с информацией о пользователе (`email`, `name`, `picture`).

### 5. Security Headers, CORS, CSRF
- **Security Headers:** Заголовки, которые говорят браузеру, как безопасно обрабатывать ваш сайт. `Content-Security-Policy` (CSP), `X-Content-Type-Options`, `Strict-Transport-Security (HSTS)`, `X-Frame-Options`.
- **CORS:** Механизм браузера, блокирующий запросы с других доменов. Настраивается через `Access-Control-Allow-Origin`. Не используйте `*` в production.
- **CSRF (Cross-Site Request Forgery):** Атака, когда злой сайт отправляет запрос от имени авторизованного пользователя. Защита: `SameSite=Strict/Lax` для куки, или CSRF-токен для stateful-сессий. Для чистого REST API с JWT в заголовке `Authorization` CSRF обычно не нужен.
- **Важные моменты для изучения:**
  - ✅ Используйте библиотеки типа `unrolled/secure` или `go-chi/cors` для автоматической установки заголовков.
  - ✅ CORS ≠ защита от взлома сервера. Это защита **браузера пользователя**. Для server-to-server запросов CORS не применяется.
  - ✅ Всегда включайте `HSTS` на HTTPS-сайтах, чтобы браузер принудительно использовал шифрование даже при первом посещении.

### 6. HTTPS/TLS и защита от атак
- **HTTPS/TLS:** Шифрует весь трафик между клиентом и сервером. Без него пароли, токены и данные летят по сети в открытом виде.
- **Как настроить:** `tls.Config{}` + сертификат. В dev: самоподписанные. В prod: Let's Encrypt (через Caddy/Traefik или certbot) или облачные Load Balancers.
- **Защита от инъекций/XSS/Brute-force:**
  - **SQL-инъекции:** используйте параметризованные запросы (`$1`, `?`), никогда не склеивайте строки.
  - **XSS:** экранируйте вывод в HTML, используйте `html/template`, не выводите непроверенный ввод в DOM.
  - **Brute-force:** ограничьте попытки входа (lockout на 15 мин после 5 неудач), используйте rate limiting на `/auth/login`, добавьте CAPTCHA для публичных форм.
- **Важные моменты для изучения:**
  - ✅ В Go `http.Server` поддерживает TLS из коробки: `srv.ListenAndServeTLS(certFile, keyFile)`.
  - ✅ Не коммитьте `.pem`/`.key` файлы в Git! Используйте секреты, `.env` или KMS.
  - ✅ Регулярно обновляйте зависимости. Уязвимости часто закрываются в новых версиях библиотек.

## 🛠 Практика (пошагово)

1. **Регистрация и Хеширование**
   - Создайте `POST /auth/register`. Принимайте `email`, `password`.
   - Хешируйте пароль: `hash, _ := bcrypt.GenerateFromPassword([]byte(password), bcrypt.DefaultCost)`
   - Сохраняйте `hash` в БД. Никогда не сохраняйте plain-text.

2. **Логин и JWT**
   - Создайте `POST /auth/login`. Ищите пользователя по email.
   - Проверяйте пароль: `bcrypt.CompareHashAndPassword(hashFromDB, []byte(password))`
   - Генерируйте JWT: `claims := jwt.MapClaims{"user_id": id, "exp": time.Now().Add(15*time.Minute).Unix()}`
   - Подписывайте и возвращайте: `tokenString, _ := jwt.NewWithClaims(jwt.SigningMethodHS256, claims).SignedString(secret)`

3. **Auth Middleware**
   - Пишете middleware, который читает `Authorization: Bearer <token>`
   - Валидирует через `jwt.Parse(token, func(t *jwt.Token) { return secret, nil })`
   - При успехе: кладёт `user_id` в `context`, вызывает `next.ServeHTTP`
   - При ошибке: возвращает `401 Unauthorized`

4. **Refresh Token Flow**
   - Добавьте `/auth/refresh`. Принимает `refresh_token`.
   - Проверяет его валидность и наличие в БД/Redis.
   - Генерирует новую пару `access` + `refresh`, аннулирует старый.
   - Возвращает новые токены.

5. **HTTPS (Dev-режим)**
   - Сгенерируйте самоподписанный сертификат: `openssl req -x509 -newkey rsa:4096 -keyout key.pem -out cert.pem -days 365 -nodes`
   - Запустите сервер: `srv.ListenAndServeTLS("cert.pem", "key.pem")`
   - Проверьте через `curl -k https://localhost:8080/health`

✅ **Чек-лист завершения модуля:**
- [ ] Пароли хешируются через `bcrypt` перед записью в БД
- [ ] Логин проверяет хеш, возвращает JWT с `exp` и `user_id`
- [ ] Middleware проверяет JWT, возвращает `401` при просрочке/подделке
- [ ] Реализован refresh token flow с rotation и инвалидацией
- [ ] Добавлены security headers (HSTS, X-Content-Type-Options, CSP)
- [ ] CORS настроен корректно (указан конкретный origin, не `*`)
- [ ] Сервер запускается по HTTPS (dev-режим с самоподписанным сертификатом)
- [ ] Реализована защита от brute-force (rate limit или lockout на `/auth/login`)
