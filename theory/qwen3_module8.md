## 📚 Подробный разбор тем

### 1. Структурированное логирование (`log/slog`)
- **Простыми словами:** Обычный лог — это просто текст в файле. Структурированный лог — это JSON с полями: `{"level":"error","msg":"db failed","request_id":"abc-123","duration_ms":450}`. Такие логи легко искать, фильтровать и строить по ним графики.
- **Важные моменты для изучения:**
  - ✅ В Go 1.21+ встроен `log/slog`. Не нужно тянуть внешние библиотеки, если нет специфичных требований.
  - ✅ Используйте уровни: `Debug` (отладка), `Info` (нормальная работа), `Warn` (проблема, но сервис работает), `Error` (сбой операции).
  - ✅ Всегда привязывайте `request_id` и `user_id` к логам через `slog.With()` или `context`. Иначе в логах будет каша из тысяч одновременных запросов.
  - 🚫 **Никогда не логируйте секреты:** пароли, токены, полные тела запросов с персональными данными.
  - 💡 В production используйте `slog.NewJSONHandler`. В разработке — `slog.NewTextHandler` для читаемости в консоли.

### 2. Метрики (`prometheus/client_golang`)
- **Простыми словами:** Это "приборная панель" вашего сервиса. Считает, сколько запросов пришло, сколько упало с ошибкой, как долго выполнялись запросы и сколько соединений открыто к БД.
- **Типы метрик в Prometheus:**
  - `Counter` — только растёт (количество запросов, ошибок). Сбрасывается только при перезапуске.
  - `Gauge` — может расти и падать (число активных горутин, размер пула соединений, очередь задач).
  - `Histogram` / `Summary` — измеряют распределение (латентность запросов, размер тела ответа).
- **Важные моменты для изучения:**
  - ✅ Эндпоинт `/metrics` отдаёт данные в формате, который понимает Prometheus. Он **не требует авторизации** по умолчанию → в production закрывайте его или ограничивайте доступ.
  - ✅ **Осторожно с cardinality (кардинальностью):** Не используйте метки с уникальными значениями (`user_id`, `request_id`, `email`). Это создаст миллионы уникальных временных рядов и "положит" Prometheus. Используйте только `method`, `status`, `route`.
  - ✅ Используйте готовые обёртки: `promhttp.Handler()` для HTTP-метрик, `grpcprometheus` для gRPC.

### 3. Распределённый трейсинг (OpenTelemetry)
- **Простыми словами:** Если один запрос пользователя проходит через 3 микросервиса и БД, как понять, где именно он "застрял" на 2 секунды? Трейсинг рисует "дерево" выполнения с точными временными метками на каждом шаге.
- **Ключевые понятия:**
  - `Trace` — весь путь запроса от клиента до ответа.
  - `Span` — отдельный шаг в пути (HTTP-запрос, SQL-запрос, вызов к внешнему API).
  - `Context Propagation` — передача `trace_id` между сервисами через заголовки.
- **Важные моменты для изучения:**
  - ✅ OpenTelemetry (OTel) — индустриальный стандарт. Поддерживается Jaeger, Grafana Tempo, AWS X-Ray.
  - ✅ Используйте `otelhttp` и `otelgrpc` для автоматической инструментации. Они сами создают спаны для входящих/исходящих запросов.
  - ✅ **Sampling (сэмплирование):** В production не трассируйте 100% запросов (слишком много данных и оверхед). Настраивайте `TraceIDRatioBased(0.1)` → 10% запросов.
  - ⚠️ Трейсинг не заменяет логи. Они дополняют друг друга: логи = "что произошло", трейс = "где и сколько времени".

### 4. Healthchecks: Liveness & Readiness
- **Простыми словами:** Оркестраторы (Kubernetes, Docker Swarm, облачные провайдеры) постоянно спрашивают ваш сервис: "Ты жив?" и "Ты готов принимать трафик?".
- **Разница:**
  - `/health` (Liveness) → "Я вообще запущен?". Если `500` → оркестратор перезапускает контейнер.
  - `/ready` (Readiness) → "Я подключён к БД, кешу и очередям?". Если `503` → оркестратор временно не шлёт новые запросы, но не перезапускает.
- **Важные моменты для изучения:**
  - ✅ `/ready` должен делать лёгкую проверку (`db.PingContext(ctx, 1*time.Second)`), а не тяжёлый запрос `SELECT COUNT(*)`.
  - ✅ Не смешивайте их в один эндпоинт. Оркестраторы реагируют на них по-разному.
  - ✅ В `/health` не проверяйте внешние зависимости. Если внешний сервис упал, ваш сервис всё ещё "жив" и может отдавать кеш или статику.

### 5. Docker: Multi-stage Build и минимальные образы
- **Простыми словами:** Как упаковать Go-приложение так, чтобы оно весило 15 МБ, а не 800 МБ, и работало максимально безопасно.
- **Как работает Multi-stage:**
  1. `Stage 1: builder` — полная среда Go, `go build -o app`, тесты, линтеры.
  2. `Stage 2: runtime` — пустой образ (`scratch` или `distroless`), копируется только бинарник и сертификаты.
- **Важные моменты для изучения:**
  - ✅ `CGO_ENABLED=0 go build` → статическая линковка. Бинарник не зависит от системных библиотек.
  - ✅ Копируйте `go.mod` и `go.sum` **отдельно** до кода: `COPY go.mod go.sum ./` → `RUN go mod download`. Это кеширует слой зависимостей и ускоряет сборку в CI.
  - ✅ Не запускайте контейнер от `root`. Создайте непривилегированного пользователя: `USER appuser`.
  - 📦 `distroless` образы от Google не содержат shell, пакетных менеджеров и лишних утилит → меньше поверхность для атак.

### 6. Unified Graceful Shutdown & CI/CD Basics
- **Простыми словами:** Корректное завершение HTTP и gRPC серверов одновременно + автоматическая проверка кода перед тем, как он попадёт в production.
- **Graceful Shutdown:**
  - Ловим сигнал → отменяем `context` → останавливаем HTTP → останавливаем gRPC → закрываем БД → выходим.
  - Используйте `errgroup` или канал `done` для синхронизации завершения горутин.
- **CI/CD Basics:**
  - `golangci-lint` — комбайн из 50+ линтеров. Находит баги, утечки, стилистические ошибки.
  - Пайплайн: `lint` → `test` → `build` → `push image` → `deploy`.
- **Важные моменты для изучения:**
  - ✅ Настройте `.golangci.yml` под проект. Включите `errcheck`, `gocritic`, `revive`, `sqlclosecheck`.
  - ✅ CI должен падать при любом ворнинге. Не мерджьте код с `warning: unused variable`.
  - ✅ Используйте `docker buildx` для кросс-компиляции (amd64, arm64) в одном пайплайне.

## 🛠 Практика (пошагово)

1. **Логи + Request ID**
   - Замените `log.Println` на `slog`.
   - Настройте `JSONHandler` в prod, `TextHandler` в dev.
   - Пробросьте `request_id` из middleware во все логи через `ctx = context.WithValue(ctx, "request_id", id)`.

2. **Prometheus-метрики**
   - Подключите `promhttp` и зарегистрируйте `/metrics`.
   - Добавьте кастомный `HistogramVec` для времени выполнения хендлеров.
   - Проверьте в браузере `http://localhost:8080/metrics`.

3. **OpenTelemetry Tracer**
   - Инициализируйте OTel SDK с `ConsoleExporter` (для dev).
   - Оберните роутер в `otelhttp.NewHandler`.
   - Выполните запрос, посмотрите в консоли вывод спанов.

4. **Healthchecks**
   - Реализуйте `/health` → всегда `200 {"status":"ok"}`.
   - Реализуйте `/ready` → проверяет `db.Ping()`, возвращает `200` или `503`.
   - Протестируйте через `curl -w "%{http_code}"`.

5. **Dockerfile (multi-stage)**
   - Напишите `Dockerfile` с `builder` → `runtime` (`gcr.io/distroless/static:nonroot`).
   - Соберите: `docker build -t myapp:latest .`
   - Запустите: `docker run -p 8080:8080 myapp:latest`.

6. **Graceful Shutdown + golangci-lint**
   - Объедините остановку HTTP и gRPC через `errgroup`.
   - Запустите `golangci-lint run`, исправьте все ошибки.
   - Настройте `.golangci.yml` (минимум: `run.timeout: 5m`, `linters.enable: [errcheck, gocritic, revive]`).
