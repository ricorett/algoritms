## 📚 Подробный разбор тем

### 1. Protocol Buffers (`proto3`) — Контракт вместо догадок
- **Простыми словами:** Это язык описания ваших данных и функций. Вы пишете `.proto` файл → из него генерируется код на Go. Это единственный источник правды. Если поменяли контракт, код не соберётся, пока не обновите всё.
- **Ключевые элементы:** `syntax = "proto3"`, `package`, `message` (структуры), `service` + `rpc` (методы), типы полей (`string`, `int32`, `bool`, `repeated`, `map`).
- **Важные моменты для изучения:**
  - ✅ **Номера полей (field numbers) — священные.** `= 1`, `= 2`. Никогда не меняйте их после релиза и не используйте удалённые номера снова (используйте `reserved`). Иначе данные сломаются при десериализации.
  - ✅ `optional` и `oneof` появились в `proto3`. Используйте `oneof` для полей, которые взаимно исключают друг друга (например, `error_type: string` ИЛИ `code: int32`).
  - 📦 **Комментарии в `.proto` — это будущая документация.** Пишите их сразу. Генераторы и `protoc-gen-doc` подхватят их автоматически.

### 2. Генерация кода (`protoc` + плагины)
- **Простыми словами:** Компилятор `protoc` читает `.proto` и создаёт Go-файлы. Но сам он не знает Go. Ему нужны плагины: `protoc-gen-go` (для данных) и `protoc-gen-go-grpc` (для сервера/клиента).
- **Как работает:** `protoc --go_out=. --go-grpc_out=. user.proto` → получаете `user.pb.go` и `user_grpc.pb.go`.
- **Важные моменты для изучения:**
  - ✅ **Версионируйте плагины через `go install`**, а не `apt`/`brew`. Разные версии могут генерировать несовместимый код.
  - ✅ Добавьте генерацию в `Makefile` или `Taskfile`. **Никогда не редактируйте `*.pb.go` вручную** — они перезапишутся при следующей сборке.
  - 💡 **Совет:** В современном Go часто используют `buf.build` — это обёртка над `protoc`, которая упрощает управление зависимостями, линтинг `.proto` и генерацию. Изучите её, когда освоите базовый `protoc`.
  - ⚠️ Если видите ошибки типа `undefined: grpc.ClientConnInterface`, проверьте версии `google.golang.org/grpc` и `protoc-gen-go-grpc` (должны быть совместимы).

### 3. gRPC Server: запуск и регистрация
- **Простыми словами:** Сервер gRPC — это отдельный процесс, слушающий TCP-порт. В отличие от HTTP, он не парсит строки запросов, а сразу читает бинарные данные по строгому контракту.
- **Базовый код:**
  ```go
  lis, _ := net.Listen("tcp", ":50051")
  s := grpc.NewServer()
  pb.RegisterUserServiceServer(s, &myServer{})
  s.Serve(lis) // Блокирующий вызов!
  ```
- **Важные моменты для изучения:**
    - ✅ `grpc.NewServer()` принимает опции: `grpc.KeepaliveParams`, `grpc.MaxRecvMsgSize`, `grpc.UnaryInterceptor`. Настраивайте их сразу, а не постфактум.
    - ✅ `s.Serve()` блокирует поток. Для graceful shutdown запускайте в отдельной горутине или используйте `s.GracefulStop()`, передавая сигнал от `os/signal`.
    - 🚫 Не мешайте gRPC и HTTP на одном порту без специального прокси. Они говорят на разных "языках".

### 4. Типы вызовов: Unary vs Streaming
- **Простыми словами:** В REST всё — это запрос/ответ. В gRPC есть 4 режима:
    1. **Unary:** Один запрос → один ответ (как обычный REST POST/GET).
    2. **Server Streaming:** Один запрос → поток ответов (например, подписка на обновления).
    3. **Client Streaming:** Поток запросов → один ответ (загрузка файла частями).
    4. **Bidirectional:** Оба потока одновременно (чат, real-time аналитика).
- **Важные моменты для изучения:**
    - ✅ **Начинайте с Unary.** Стриминг добавляет сложность (контексты, каналы, управление памятью, обработка обрывов соединения).
    - ✅ В Go стримы реализуются через интерфейсы с методами `Recv()` и `Send()`. Всегда проверяйте `err == io.EOF` — это признак конца потока.
    - ⚠️ Стримы держат соединение открытым. Помните про таймауты и `keepalive`, иначе "зомби"-соединения съедят память сервера.

### 5. Интерцепторы (Middleware для gRPC)
- **Простыми словами:** Это аналог HTTP-middleware, но для gRPC. Перехватывают вызов до и после выполнения метода. Бывают `Unary` и `Stream`.
- **Цепочка:** `Auth → Logging → Metrics → Recovery → Handler`
- **Как работает:** Функция принимает `context`, запрос, инфо о методе и `handler`. Вызывает `handler(ctx, req)`, обрабатывает результат, возвращает.
- **Важные моменты для изучения:**
    - ✅ Используйте `github.com/grpc-ecosystem/go-grpc-middleware/v2` и `chain` для сборки цепочки. Не пишите вложенные `func` вручную.
    - ✅ Извлекайте метаданные (`metadata.FromIncomingContext(ctx)`) для токенов, `request_id`, трейсинга.
    - ✅ **Recovery обязателен!** gRPC не ловит паники автоматически. Если сервис упадёт, клиент получит разорванное соединение без объяснений.
    - ⚠️ Не блокируйте интерцепторы долгими операциями. Они выполняются в том же потоке, что и обработчик.

### 6. HTTP/JSON мост (`grpc-gateway`)
- **Простыми словами:** gRPC бинарный. Браузеры и `curl` не умеют с ним работать напрямую. `grpc-gateway` — это обратный прокси, который генерирует обычный HTTP/JSON сервер, перенаправляющий запросы в ваш gRPC-сервер.
- **Как работает:** В `.proto` добавляете аннотации `google.api.http`, запускаете генератор → получаете `*_gateway.pb.go`.
- **Важные моменты для изучения:**
    - ✅ Gateway и gRPC-сервер **работают на разных портах** (например, `:8080` для HTTP, `:50051` для gRPC).
    - ✅ Аннотации в `.proto`: `option (google.api.http) = { get: "/v1/users/{id}" };`
    - ✅ Gateway автоматически маппит gRPC-ошибки в HTTP-статусы (`NOT_FOUND` → `404`, `INVALID_ARGUMENT` → `400`).
    - ⚠️ Стриминг в gateway имеет ограничения. Для сложных real-time кейсов лучше использовать WebSockets или SSE отдельно.

### 7. Статусы и ошибки gRPC
- **Простыми словами:** В HTTP мы возвращаем `200`, `404`, `500`. В gRPC используется `google.rpc.Code`. Это строго типизированные коды: `OK`, `INVALID_ARGUMENT`, `NOT_FOUND`, `UNAUTHENTICATED`, `INTERNAL` и др.
- **Как работать:**
  ```go
  return nil, status.Error(codes.NotFound, "user not found")
  // Или с деталями:
  st := status.New(codes.InvalidArgument, "bad request")
  st, _ = st.WithDetails(&pb.ErrorDetail{Field: "email", Reason: "invalid format"})
  return nil, st.Err()
  ```
- **Важные моменты для изучения:**
    - ✅ **Не используйте HTTP-коды в gRPC.** Используйте `codes.*`. Gateway сам переведёт их в HTTP.
    - ✅ На клиенте используйте `status.FromError(err)` чтобы извлечь код и детали.
    - ✅ Логируйте `codes.Internal` как критичные, а `codes.InvalidArgument` как ошибки клиента. Это упростит мониторинг.

## 🛠 Практика (пошагово)

1. **Создайте `.proto` файл**
    - Опишите `message User`, `message CreateUserRequest`, `message GetUserResponse`.
    - Определите сервис `UserService` с методами `CreateUser` и `GetUser`.
    - Добавьте аннотации `google.api.http` для gateway (`import "google/api/annotations.proto"`).

2. **Генерация кода**
    - Установите `protoc` и 3 плагина: `protoc-gen-go`, `protoc-gen-go-grpc`, `protoc-gen-grpc-gateway`.
    - Напишите скрипт/Makefile для генерации. Запустите, проверьте появившиеся файлы.

3. **Реализация сервера**
    - Создайте структуру `server struct { pb.UnimplementedUserServiceServer }`.
    - Реализуйте методы `CreateUser`, `GetUser` с заглушками (пока возврат моковых данных).
    - Запустите `grpc.NewServer()`, зарегистрируйте сервис, слушайте порт `:50051`.

4. **Интерцепторы**
    - Добавьте логгер (выводит метод, время, статус).
    - Добавьте Recovery (`defer recover()`).
    - Соберите цепочку через `middleware.ChainUnaryServer`.

5. **gRPC-Gateway**
    - Сгенерируйте gateway-файлы.
    - Запустите HTTP-сервер на `:8080`, который проксирует запросы в `:50051`.
    - Проверьте через `curl http://localhost:8080/v1/users/1`.

6. **Тестирование через `grpcurl`**
    - `grpcurl -plaintext -d '{"email":"test@test.com"}' localhost:50051 UserService.CreateUser`
    - Убедитесь, что сервер отвечает, а логи пишутся корректно.
