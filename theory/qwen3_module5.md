## 📚 Подробный разбор тем

### 1. RESTful принципы и дизайн API
- **Простыми словами:** REST — это набор договорённостей, как называть URL-ы и какие методы использовать, чтобы любой разработчик сразу понял, как работать с вашим сервисом.
- **Основные правила:**
  - ✅ **Ресурсы во множественном числе:** `/users`, `/orders`, `/payments` (не `/user` или `/getUsers`)
  - ✅ **Методы = действия:** 
    - `GET` → прочитать (безопасный, идемпотентный)
    - `POST` → создать
    - `PUT` → полностью заменить
    - `PATCH` → частично обновить
    - `DELETE` → удалить
  - ✅ **Идемпотентность:** Повторный вызов `PUT`/`DELETE` с теми же данными не должен менять состояние системы. `POST` — не идемпотентен (может создать дубликат).
  - ✅ **Статус-коды по смыслу:** `200` (ОК), `201` (Создано), `204` (Успешно, без тела), `400` (Ошибка клиента), `404` (Не найдено), `409` (Конфликт, например дубликат email), `500` (Ошибка сервера).
- **⚠️ Важно:** Не смешивайте действия и ресурсы. `POST /users/5/activate` → плохо. Лучше: `PATCH /users/5` с телом `{"status": "active"}`. Или используйте отдельный ресурс `/activations`.

### 2. Пагинация, фильтрация, сортировка
- **Простыми словами:** Как отдавать данные частями и позволять клиенту выбирать нужное, чтобы не «завалить» сервер и не тратить трафик.
- **Пагинация:**
  - `Offset/Limit` (`?limit=20&offset=40`) — просто, но на больших смещениях (`offset=100000`) БД сканирует и пропускает сотни тысяч строк → медленно.
  - `Cursor-based` (`?cursor=eyJpZCI6MTIzfQ&limit=20`) — берёт `id` или `created_at` последней записи, ищет дальше. Быстро, стабильно, но сложнее в реализации.
- **Фильтрация и сортировка:**
  - Фильтры: `?status=active&role=admin`
  - Сортировка: `?sort=-created_at,name` (минус = по убыванию)
- **⚠️ Важно:** 
  - Всегда возвращайте метаданные: `total_count`, `next_cursor`, `has_more`.
  - Индексируйте в БД поля, по которым фильтруете и сортируете, иначе пагинация убьёт производительность.
  - Ограничивайте `limit` сверху (например, `max_limit=100`), чтобы клиент не запросил миллион строк за раз.

### 3. Rate Limiting (Ограничение запросов)
- **Простыми словами:** «Не больше N запросов в минуту от одного IP или пользователя». Защита от спама, парсинга и случайного DDoS.
- **Как работает:**
  - **Token Bucket / Sliding Window:** Алгоритмы, которые считают запросы и разрешают только разрешённое количество.
  - В Go из коробки: `golang.org/x/time/rate` (простой in-memory лимитер).
  - Заголовки ответа для клиента: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`.
- **⚠️ Важно:**
  - `x/time/rate` работает **только в памяти одного процесса**. Если у вас 3 реплики сервера, лимит будет `N * 3`. Для production используйте Redis или внешний API Gateway.
  - При превышении лимита всегда возвращайте `429 Too Many Requests` + заголовок `Retry-After`.
  - Не ограничивайте критичные эндпоинты типа `/health` или вебхуки от платёжных систем.

### 4. Кеширование ответов
- **Простыми словами:** Сохранять результат тяжёлого запроса, чтобы следующий раз отдать его мгновенно, не трогая БД и не выполняя сложные вычисления.
- **Уровни кеширования:**
  1. **HTTP-кеш (заголовки):** `Cache-Control: public, max-age=60` → браузер/прокси хранит 60 сек. `ETag`/`Last-Modified` → клиент спрашивает «изменилось ли?», сервер отвечает `304 Not Modified`.
  2. **In-memory (в процессе Go):** `sync.Map`, `freecache`, `bigcache`. Мгновенный доступ, но теряется при рестарте.
  3. **Распределённый (Redis/Memcached):** Хранится отдельно, живёт между рестартами, работает на нескольких серверах.
- **⚠️ Важно:**
  - Никогда не кешируйте приватные данные (`Authorization`, персональные профили) без явного указания `private`.
  - Продумывайте **инвалидацию** (очистку) кеша при обновлении данных. Устаревший кеш → баги на фронтенде.
  - Кешируйте только `GET`-запросы, которые не меняют состояние.

### 5. Автодокументация (OpenAPI / Swagger)
- **Простыми словами:** Описание вашего API в машиночитаемом формате. Фронтенд генерирует клиенты, тесты читают контракты, новые разработчики не задают глупых вопросов.
- **Как работает в Go (`swaggo/swag`):**
  - Вы пишете специальные комментарии прямо над хендлерами:
    ```go
    // @Summary Получить пользователя
    // @Description Возвращает профиль пользователя по ID
    // @Tags users
    // @Accept json
    // @Produce json
    // @Param id path int true "ID пользователя"
    // @Success 200 {object} UserResponse
    // @Failure 404 {object} ErrorResponse
    // @Router /users/{id} [get]
    func GetUserHandler(c echo.Context) error { ... }
    ```
  - Команда `swag init` сканирует код → создаёт `docs/swagger.json` и `docs/swagger.yaml`.
  - Подключаете `swaggerFiles.Handler` → открываете `/swagger/index.html` в браузере.
- **⚠️ Важно:**
  - Документация должна быть **живой**. Запустите `swag init` в CI или при сборке, иначе она устареет за день.
  - Не дублируйте типы в документации и в Go-коде. `swag` сам подхватит структуры из `json`-тегов.

### 6. Тестирование HTTP-хендлеров (`httptest`)
- **Простыми словами:** Проверять, что сервер отвечает правильно, не поднимая реальный порт, не стучась в сеть и не ломая БД.
- **Ключевые инструменты:**
  - `httptest.NewRequest(method, url, body)` → создаёт фейковый запрос в памяти.
  - `httptest.NewRecorder()` → «ловит» ответ сервера (статус, заголовки, тело).
  - `httptest.NewServer(handler)` → запускает сервер на случайном порте (для интеграционных тестов с внешними зависимостями).
- **Паттерн Table-Driven Tests (стандарт Go):**
  ```go
  tests := []struct {
      name       string
      reqBody    string
      wantStatus int
      wantError  string
  }{
      {"Валидный запрос", `{"email":"a@b.com"}`, 201, ""},
      {"Пустой email", `{"email":""}`, 400, "email required"},
  }
  for _, tt := range tests {
      t.Run(tt.name, func(t *testing.T) {
          // 1. Создаём запрос и рекордер
          // 2. Вызываем хендлер
          // 3. Сравниваем статус и тело с ожиданиями
      })
  }
  ```
- **⚠️ Важно:**
    - В unit-тестах **мокайте** репозитории и внешние сервисы. Не стучитесь в реальную БД из хендлер-тестов.
    - Проверяйте не только статус-код, но и тело ответа (JSON), и заголовки (`Content-Type`, `X-Request-Id`).
    - Используйте `json.Unmarshal` или `json.Decoder` для парсинга ответа в тесте, не сравнивайте строки посимвольно.

## 🛠 Практика (пошагово)

1. **Пагинация + Фильтрация**
    - Обновите `GET /users` на `Offset/Limit` или `Cursor`.
    - Добавьте фильтры: `?status=active` и сортировку `?sort=-created_at`.
    - Верните JSON-обёртку: `{"data": [...], "meta": {"total": 150, "limit": 20, "offset": 0}}`.

2. **Rate Limiter**
    - Подключите `golang.org/x/time/rate`.
    - Создайте middleware, который ограничивает до 100 запросов/мин на IP.
    - При превышении возвращайте `429` + заголовок `Retry-After: 60`.

3. **Swagger-документация**
    - Установите `swag` (`go install github.com/swaggo/swag/cmd/swag@latest`).
    - Добавьте комментарии к `GET /users`, `POST /users`, `GET /health`.
    - Запустите `swag init`, подключите UI, откройте в браузере и попробуйте отправить запрос из UI.

4. **Тесты хендлеров**
    - Напишите table-driven тесты для `POST /users` (успех, валидация, дубликат email).
    - Замокайте `UserRepository` через интерфейс.
    - Проверьте статус-код, тело ответа и вызов методов мока (`mock.AssertExpectations(t)`).
