## 🎯 Цель модуля
Научиться выстраивать предсказуемый «конвейер» обработки HTTP-запроса. Добавить сквозные задачи (логирование, ошибки, безопасность), парсить данные из разных источников, валидировать их и возвращать ответы в едином формате.

## 📚 Подробный разбор тем

### 1. Паттерн Middleware (Промежуточное ПО)
- **Простыми словами:** Это как проверка на входе в клуб. Охранник проверяет дресс-код, потом кассир берёт деньги, потом бармен наливает напиток. Каждый делает своё дело и передаёт человека дальше.
- **Как выглядит в Go:** Функция принимает `http.Handler`, создаёт новый `http.Handler` и внутри вызывает `next.ServeHTTP(w, r)`.
- **Важные моменты для изучения:**
  - ✅ **Порядок имеет значение:** `Logger → Recovery → CORS → Auth → Router`. Если поставить `Auth` до `Recovery`, паника в проверке токена уронит сервер.
  - ✅ **Всегда вызывайте `next.ServeHTTP()`:** Если забыть, запрос «зависнет» и клиент получит таймаут.
  - ✅ **Не усложняйте:** Один middleware = одна задача. Логгер только логирует, Auth только проверяет токен.
  - ⚠️ **Осторожно с замыканиями:** Middleware часто создают функции внутри функций. Следите, чтобы не «запирать» в памяти большие объекты.

### 2. Сквозные задачи (Cross-Cutting Concerns)
Это задачи, которые нужны почти в каждом запросе, но не относятся к бизнес-логике.

| Задача | Зачем нужна | Как реализовать (просто) |
|--------|-------------|--------------------------|
| **Логирование** | Понимать, кто, куда и как долго стучался | Запомнить `time.Now()`, после `next.ServeHTTP()` вычислить `time.Since(start)`, вывести метод, путь, статус, время |
| **Recovery** | Ловить `panic`, чтобы сервер не упал из-за одного запроса | `defer func() { if r := recover(); r != nil { log.Println(r); http.Error(w, "internal error", 500) } }()` |
| **CORS** | Разрешить браузеру с другого сайта делать запросы к вашему API | Добавить заголовки `Access-Control-Allow-Origin`, `Methods`, `Headers`. Для `OPTIONS` (preflight) вернуть `204` сразу |
| **Request ID** | Отслеживать один запрос в логах от начала до конца | Сгенерировать UUID, положить в `context` и заголовок ответа `X-Request-Id` |

- **Важный момент:** `Recovery` должен быть **первым** или вторым в цепочке, чтобы ловить паники из всех последующих middleware.

### 3. Парсинг входящих данных
Данные приходят к серверу в разных «упаковках». Нужно уметь их распаковывать.

- **Query-параметры** (`/search?q=go&page=1`)
  - `r.URL.Query().Get("q")` → возвращает строку или `""`
  - `r.URL.Query()["tags"]` → возвращает `[]string` (если `?tags=a&tags=b`)
- **Form Data** (`application/x-www-form-urlencoded`)
  - `r.FormValue("email")` или `r.ParseForm()` → работает для HTML-форм
- **JSON-тело** (`application/json`)
  - `json.NewDecoder(r.Body).Decode(&user)`
  - ⚠️ `r.Body` — это поток. Читать можно **только один раз**. После чтения закройте: `defer r.Body.Close()`
- **Файлы (Multipart)** (`multipart/form-data`)
  - `r.ParseMultipartForm(10 << 20)` → лимит 10 МБ
  - `file, header, err := r.FormFile("avatar")`
- **Важные моменты:**
  - 🔒 Всегда ограничивайте размер тела: `r.Body = http.MaxBytesReader(w, r.Body, 1<<20)` (1 МБ). Иначе злоумышленник может отправить 10 ГБ и «задушить» память сервера.
  - 🔍 Проверяйте `Content-Type` перед парсингом JSON. Если клиент пришлёт XML в JSON-эндпоинт, сервер упадёт или вернёт 500.

### 4. Валидация входящих данных
- **Ручная проверка:**
  ```go
  if user.Email == "" {
      return errors.New("email обязателен")
  }
  if user.Age < 18 {
      return errors.New("возраст должен быть >= 18")
  }
  ```
  👉 *Плюсы:* полный контроль. *Минусы:* много кода, легко забыть проверку.
- **Через теги + `go-playground/validator`:**
  ```go
  type User struct {
      Email string `json:"email" validate:"required,email"`
      Age   int    `json:"age" validate:"min=18,max=120"`
  }
  validate := validator.New()
  err := validate.Struct(user)
  ```
- **Важные моменты:**
  - ✅ Валидация должна происходить **до** попадания данных в бизнес-логику.
  - ✅ Не доверяйте клиенту. Даже если фронтенд проверяет данные, бэкенд должен проверять их повторно.
  - 📦 Собирайте все ошибки валидации в один срез, а не останавливайтесь на первой. Клиенту проще исправить всё за раз.

### 5. Стандартизация ответов и обработка ошибок
- **Почему это важно:** Фронтенд/мобильное приложение всегда должно знать, где искать данные, а где сообщение об ошибке.
- **Единый формат ответа (`ResponseEnvelope`):**
  ```go
  type Response struct {
      Success bool        `json:"success"`
      Data    interface{} `json:"data,omitempty"`
      Error   string      `json:"error,omitempty"`
  }
  ```
- **Обработка ошибок через `errors.Is` / `errors.As`:**
  - В Go 1.13+ ошибки можно «заворачивать»: `fmt.Errorf("не удалось создать пользователя: %w", err)`
  - `errors.Is(err, sql.ErrNoRows)` → проверяет, есть ли в цепочке эта ошибка
  - `errors.As(err, &httpErr)` → извлекает ошибку нужного типа
  👉 *Простыми словами:* Сравниваем ошибки по смыслу, а не по тексту. Это спасает от хаоса при рефакторинге.
- **Централизованный `ErrorHandler`:**
  Одна функция, которая принимает `err`, смотрит на его тип и возвращает нужный HTTP-статус + сообщение. Не пишите `if err != nil { http.Error(...) }` в каждом хендлере.

### 6. Работа с контекстом (`context`)
- **Зачем:** Передавать «попутную» информацию (кто пользователь, ID запроса, дедлайн) вглубь вызовов без глобальных переменных и лишних аргументов.
- **`context.WithValue`:**
  ```go
  ctx := context.WithValue(r.Context(), "userID", 42)
  r = r.WithContext(ctx)
  ```
  👉 *Простыми словами:* Кладём записку в конверт запроса. Внизу цепочки достаём: `id, _ := ctx.Value("userID").(int)`
- **`context.WithTimeout` / `WithDeadline`:**
  Ограничивает время выполнения. Если клиент отключился или запрос тянется слишком долго, сервер сам отменит тяжёлую операцию к БД.
  ```go
  ctx, cancel := context.WithTimeout(r.Context(), 5*time.Second)
  defer cancel()
  db.QueryContext(ctx, "SELECT ...")
  ```
- **Важные моменты:**
  - 🚫 Не используйте `context` для передачи опциональных параметров (например, `skipPagination`). Для этого есть отдельные аргументы.
  - ✅ Всегда передавайте `ctx` в вызовы БД, HTTP-клиентов и gRPC. Без него отмена запроса клиентом не сработает.
  - 🔑 Ключи для `WithValue` лучше делать не строками, а типизированными: `type ctxKey string` + `const UserIDKey ctxKey = "userID"`. Это защищает от случайных коллизий.

## 🛠 Практика (пошагово)

1. **Соберите цепочку middleware**
   - Напишите функции: `Logger`, `Recover`, `CORS`, `SetRequestID`, `FakeAuth` (просто проверяет наличие заголовка `Authorization`)
   - Соберите их в одну: `handler = SetRequestID(Recover(CORS(Logger(FakeAuth(router)))))`
   - Проверьте в логах: появляется ли `request_id`, сохраняется ли после паники, возвращается ли CORS-заголовки.

2. **Парсинг + Валидация**
   - Создайте `POST /users`. Принимайте JSON.
   - Ограничьте размер тела до 1 МБ.
   - Распарсите в структуру, прогоните через `validator`.
   - При ошибках валидации верните `400` со списком проблемных полей.

3. **Централизованный ErrorHandler**
   - Создайте функцию `WriteError(w, err, fallbackCode int)`
   - Внутри: `switch { case errors.Is(err, ErrNotFound): code = 404; case errors.Is(err, ErrUnauthorized): code = 401; default: code = 500 }`
   - Возвращайте JSON в формате `ResponseEnvelope`.

4. **Контекст в действии**
   - В `FakeAuth` middleware извлеките `user_id` из заголовка (пока захардкоженный или любой строковый), положите в `context`.
   - В хендлере получите `user_id` из `r.Context()`, передайте в «репозиторий» (пока заглушку).

✅ **Чек-лист завершения модуля:**
- [ ] Запрос проходит через 4+ middleware в правильном порядке
- [ ] `panic` в бизнес-логике не роняет сервер, возвращает 500
- [ ] CORS заголовки работают, `OPTIONS` отвечает `204`
- [ ] JSON парсится безопасно (лимит размера, `defer Close()`)
- [ ] Валидация возвращает понятные ошибки по всем полям
- [ ] Все ошибки обрабатываются централизованно
- [ ] `request_id` и `user_id` пробрасываются через `context`
